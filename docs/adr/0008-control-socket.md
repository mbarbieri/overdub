# Overdub listens on an always-on local control socket, and every UI gesture and socket request runs one Intent vocabulary

Status: accepted (issue #166). Amended as issues #167 to #172 land.

A verification agent must drive every user operation of the running app and read any of its state, so a change is proven on the real app and not only in `ctest`. Before this decision the operations had no names. Each one was a lambda wired from a page callback into a private `ui::SongView` method, or one of 12 `ui::Command`s, or a chooser callback in `src/app`, which no test can reach. The side effects a user relies on lived in those methods: a pending Mixer arrow-key burst committed and carried into the next edit, the right half selected after a split, Monitoring turned off after a Track delete, clip indicators put out when a Pass starts, and refusals presented only for some gestures. A socket that called `ui::OpenSong` directly would skip them.

The decision has five parts:

- **Always on.** Every build, release included, listens on an `AF_UNIX` socket at `~/Library/Application Support/Overdub/control/control.sock`. The folder is mode 0700 and the socket is mode 0600 right after `bind`, and a peer whose uid is not the app's is refused (`getpeereid`). `OVERDUB_CONTROL=0` turns it off and `OVERDUB_CONTROL_SOCKET=<path>` moves it (tests, and several instances in worktrees). The protocol is newline-delimited JSON. A `juce::Timer` on the message thread polls the socket with `poll (..., 0)`, as `song::SeparationHelperRun` polls its helper, so no reader thread exists. Failing to listen never stops the app, and `--selftest` never listens.
- **One Intent vocabulary.** `ui::Intent` (`src/ui/Intent.h`) is a closed `std::variant` of plain structs in domain terms (ids, samples, dB, never pixels), in three groups by owner: `AppIntent` (File, settings and calibration), `WindowIntent` (`ui::MainComponent`) and `SongIntent` (`ui::SongView`), which nests `intent::Edit`, the plain one-undo-step edits. Each struct names its `op` and has a field table, from which its JSON form is derived (`src/core/Described.h`). The variant is the one list of operations: the parser, the op names and each owner's dispatch come from it.
- **One entry.** `ui::MainComponent::run (Intent, Origin) -> IntentResult` runs every Intent, whether it comes from a key, the top bar, the Edit menu, a page or the socket. It logs `ui.intent_run` (debug: `op`, `origin`) and refreshes the window, except for `preview_mix`, which a Mixer drag runs once per frame and which changes only what is heard. It keeps the modal run dialog's gate: while a Separation or a conversion runs, only `cancel_run` and the App group pass it (`ui.run_dialog_open`). The App group passes because the Settings window is outside the dialog, and the Workspace itself refuses every App Intent but `quit` and hiding the Settings window while a Separation or a conversion runs. `Origin` reaches only that log line. No handler branches on it.
- **Dialogs are answered by parameters.** A dialog only collects an Intent's fields. `import_files` carries the chosen files, and `delete_track` is the delete after the user confirmed it. The handler, not the dialog, owns every check, because the answer can come later, from the socket, or after the Song changed. The socket never opens a native dialog. What a dialog would offer is something to read instead.
- **Results are explicit.** A handler returns `core::Expected<IntentDone>`. `IntentDone` carries the id of what it created (`add_track`, the right half of `split_selected_clip`, `add_insert`'s slot) and whether it waits for an answer it asked for (camera access). An Error is what the handler handled. It is presented by its tier exactly as the gesture always presented it, or, for a gesture that does nothing, logged at debug and never presented (`ui.no_song_open`, `ui.not_in_edit_mode`, `ui.no_clip_selected`, `ui.nothing_selected`, `ui.nothing_to_undo`, `ui.nothing_to_redo`, `ui.track_already_there`, `ui.input_channels_unavailable` (input channels the device's input picker does not offer, which only the socket can name), the running activity's refusal). The Workspace's refusals of App Intents while something runs are the exception: they are presented as Notices, as their menu items and Settings buttons always presented them. Work an Intent starts and that finishes later (a Pass, an export, a Separation, a conversion) shows as log events and app state, not in its result.

## Considered Options

- **A socket adapter per operation** (a table from names to lambdas that call `SongView` or `OpenSong`): the shallowest interface, but a second hand-kept list of about 70 operations next to the UI's, and two ways to do each task. Completeness would depend on a test that lists names.
- **A dialog broker** (the socket opens the real dialogs and answers them as pending prompts): closer to the UI, but it needs two-phase requests, state per dialog kind, timeouts, and a rule for a human answering the same dialog at once. The component tests already cover the asking half of each dialog.
- **Synthetic input** (clicks at a Component path or a point, key presses): reaches everything with no vocabulary, but couples the agent to the layout, and no test can say it is complete.
- **A reader thread with a locked queue into the message thread**: no faster for local line-rate traffic, and it adds a lock and lifetime rules.
- **JUCE's transports**: `InterprocessConnection` has its own framing, `StreamingSocket` is TCP only, and `NamedPipe` creates mode 0666 files in `/tmp`.

## Consequences

- **Adding an operation** is adding a struct to `ui/Intent.h` and a handler to its owner. An owner missing a handler does not compile, and neither does a catch-all handler (`core::visitExhaustively` takes one handler per alternative). A struct without `op` and `fields` cannot be an alternative, and two equal op names fail a `static_assert`.
- **Gesture phases are not operations.** Drag frames, Esc during a drag, arrow presses in a burst and hover are UI state. What they commit is an Intent. A Mixer drag in progress is heard through `preview_mix`, which changes neither the Song nor its history.
- **Plain edits have one pure half.** `ui::editedSong` (`ui/SongEdits.h`) pairs each `intent::Edit` with its undo label. The edit handler and the Mixer's previews both use it, so the Song a gesture previews is the Song its release commits. Every edit still goes through `SongView`'s one funnel, which commits a pending arrow-key burst first, as its own undo step inside the Intent being run (no nested `ui.intent_run`), and carries its value.
- **Areas.** Event names and Error codes use the area of the `src/` folder that raises them (ADR 0006): a refusal raised in `src/ui` is `ui.*`, and a protocol error raised in `src/control` is `control.*`. ADR 0006 lists `control`.
- **Security.** Any process of the same user can drive the app while it runs, and so use the macOS privacy grants the user gave Overdub: it can record from the microphone and the camera and read and write the folders the user let Overdub reach, without its own prompt. An export through the socket overwrites the file it names. The uid check and the 0700 folder keep other users out, but nothing keeps out a same-user process. The user accepted this risk on one condition, that it stays visible (issue #177): while a client is connected, the top bar shows "CONTROLLED BY" in small caps over the process's name, or "<first name> +N" when N other processes are connected (each process is listed once, however many connections it has). The name is never scaled down: one too wide for its slot ends in an ellipsis. A client stays listed for 3 s after it disconnects, so a one-shot request that connects, runs and hangs up between two polls is still seen. The server resolves each client's process name once at connect from its peer pid (`LOCAL_PEERPID`, then `proc_name`, or `pid <n>` when that fails) and logs it as `process` on `control.client_connected`. It is the name of the process that connected: a socket passed to or inherited by another process still shows the one that connected. A client that hung up before the server accepted it has no readable pid and shows as "unknown process". The name is what the process calls itself, so it informs the user and authenticates nothing.
- **Tests** (ADR 0005). A test runs Intents through `MainComponent::run` with `Origin::control` on the real window and asserts what the UI gesture asserts. Only the socket server's own tests open a socket, at a temporary path.
- **Verification** (issue #172). The project verify skill (`.claude/skills/verify/`) proves changes on the real app through this socket. `scripts/overdub-ctl` sends one request and prints the reply. `journey-record-pass.sh`, `journey-edit.sh`, `journey-export.sh` and `journey-separation.sh` drive the record-pass, edit, export and Separation journeys with Intents and check app state, files and `afinfo` at each step. `journeys-all.sh` runs all four, each from a fresh launch. The client refuses `measure_latency` unless it is told sound is allowed, because that calibration plays test signals out of the speakers.
- **In place after issue #166.** The vocabulary, `MainComponent::run` and `SongView::run` with every Song handler. Keys, the top bar, the Edit menu, the Mixer and the Record rows' faders, Track delete, split and delete, and import run Intents. The other pages keep their callbacks, which call the same handlers, until issue #168. Since issue #168 the Edit page (its Timeline, Take Lanes, Clip toolbar, Passes panel and Mixer divider) reports every gesture that changes state as an Intent through one sink, `EditPage::onIntent`, and changes what it shows only when the handler calls back. A Clip drag names its plain edit (`ui::intentForDrag`), and `editedSong` of that edit is both the drag's preview and what its release commits. The Edit page's one other hook, the × in a Track header, asks the window to confirm before `delete_track` runs. Since issue #170 the App group runs in `ui::Workspace::run`, which `MainComponent::run` hands it (`ui.intent_not_routed` only in a window without a Workspace): the File menu's dialogs and the settings panels only collect an App Intent's fields, the calibration results are the Workspace's state whether or not the Settings window is open, and the window keeps two hooks, showing the Settings window and quitting. Since issue #171 the window keeps each Alert it shows until it closes: the default `showAlert` returns a handle that closes its window as OK does (`juce::AlertWindow::showScopedAsync`'s `ScopedMessageBox`), which the window owns, and the Alert leaves the window's list when the user closes it. `dismiss_alerts` closes every Alert in that list, logging `ui.alert_dismissed` (`code`, `tier`) for each. A second `dismiss_alerts`, or the user's OK on an Alert it already closed, does nothing. An Alert a Pass defers is not open yet: it stays queued until the Pass stops. The socket transport (`src/control/`, issue #169) answers `hello`, `subscribe`, `wait`, `state`, `ops`, `insert_plugins` and every Intent. Since issue #167 `state` reads the app state (`control/AppState.h`), `wait` also takes a JSON pointer into it, and calibration runs show there as activities. `tests/control/GestureCensusTest.cpp` fires every click, drag, wheel, pinch, drop, ComboBox item and key the window offers, in each mode, and fails when one changes the app state without a `ui.intent_run`; its `notYetMigrated` list names the page gestures issue #168 moves, and fails on an entry that no longer bypasses.
- **Protocol** (`control/Controller.h`, `control/IntentOps.h`). A request is one JSON object per line, `{"id", "op", ...fields}`. A reply is `{"id", "ok": true, "seq", ...result}` or `{"id", "ok": false, "seq", "error": {"code", "message", "fields"}}`. A reply waits until the log lines its request wrote have reached every subscriber, and its `seq` is not less than theirs. The Controller answers `hello`, `subscribe {events, level}`, `state {parts}` and `wait` itself. `state` answers the app state's sections (`control::appState`: `song`, `history`, `transport`, `activity`, `idle`, `view`, `window`, `messages`, `audio`, `calibration`, `camera`, `inserts`, `monitoring`, `meters`, `refused`), all of them without `parts`, and `control.bad_field` with `key` `parts` for a name it does not know. `messages` lists the Notice shown now (`null` while none), the open Alerts (`alerts_shown`) and the Alerts a running Pass defers (`alerts_deferred`), oldest first, each as `{code, tier, text}`. The Notice also has `counter`, the number of Notices shown up to it, so the same Notice shown again is seen, `action`, `null` or `{label, intent}` where `intent` is the Intent its button runs in the form the socket takes, and `hides_at_ms`, when it hides on its own in Unix epoch milliseconds, fixed when it was shown so reading it twice reads the same value, or `null` while it has an action, which it shows until clicked or replaced. Reading it changes nothing: the meters are the values the UI last showed, never a fresh take of the engine's peaks. `idle` is derived from `activity`, so an export or a calibration run is busy. `wait {event, since, timeout_ms}` answers `{"event", "event_seq"}` once that event is logged after `since`. `wait {pointer, equals, timeout_ms}` answers `{"pointer", "value"}` once the app state's value at the JSON pointer equals `equals`, checked at once and on every pump while such a wait is pending; the pointer's first token names the one section read. A pointer that does not resolve has no value, which is not `null`: `equals: null` waits until the pointer resolves to `null`. The value is sampled once per pump, so a change and back within one pump is missed; to see that an activity ran, wait on `/activity/counter` or `/activity/last_finish`, which only grow or change. Either wait times out with `control.wait_timed_out`, whose fields name the condition (`event` and `since`, or `pointer`, `equals` and the last `value`, or `missing: true` when the pointer did not resolve) and `timeout_ms`. `ops` answers `{"ops": [{"op", "group", "fields": [{"key", "type", ...}]}]}`, derived from the `ui::Intent` variant (`core::operationSchemas`). The group is `app`, `window` or `song`, and each field gives its JSON type, an enum field its names (`enum`), and an optional one `optional: true`. `insert_plugins` answers the AU effects on offer, `{"plugins": [{"type", "subtype", "manufacturer", "name", "version", "is_auv3"}]}`, whose first three keys are what `add_insert` names. The Controller's own op names are `Controller::ownOps` and these two are `control::appOps`. A `static_assert` keeps every Intent's op name out of both. Any other op is parsed as an Intent (`control.unknown_op` with `op`, or `control.bad_field` with `key` and `expected`) and run through `MainComponent::run` with `Origin::control`. A bad field inside a nested operation, such as `preview_mix`'s `edit`, is named by its dotted key path: `edit.volume_db`, `edit.op` with `expected` `one of its op names` for an op that field does not take, or `edit` with `expected` `operation` for a value that is not an object. An absolute path is a string that starts with `/` and holds no control character. An Intent's `IntentDone` is the reply `{"created_id": <id or null>, "awaiting_answer": <bool>}`. The Error the handler handled is the error reply, with its own code and fields plus `refused`, which is true when the running activity refused the Intent (`ui::isRefusal`).
