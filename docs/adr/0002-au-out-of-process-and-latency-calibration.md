# AUs run out-of-process; Takes are placed by reported latency plus a calibration offset

Every AU in an Insert Chain is instantiated out-of-process, in Apple's `AUHostingService`. JUCE 9 always loads AUv2 in-process (`AudioComponentInstanceNew`), so we keep a one-line patch to `external/JUCE` that passes `kAudioComponentInstantiation_LoadOutOfProcess` for AUv2 too. In the AU spike (issue #6), NeuralAmpModeler's own Cocoa view segfaulted in-process and killed the host. Out-of-process, the same plugin and its editor worked. The isolation cost about 30 µs per unit per callback, added no latency, and caused no xruns at 32 frames. Out-of-process loading is asynchronous, so a plugin can't block the message thread while it instantiates. On Apple Silicon it is also the only way to load Intel-only AUv2s.

A Take is placed at its first dry sample's timeline position minus (device input latency + output latency + graph PDC latency + **calibration offset**). JUCE's reported latency is exactly the CoreAudio device latency + safety offset + buffer + stream latency. On the built-in MacBook devices that over-reported the real round trip by a constant 821 samples (18.6 ms at 44.1 kHz) at every buffer size from 32 to 256, with 2–3 samples of jitter. So the app ships a loopback calibration (noise bursts out, cross-correlate what comes back in) that stores one offset per device and sample rate. The offset defaults to 0, so reported latency is used until the user calibrates.

## Considered Options

- **In-process by default, out-of-process per plugin or only when required**: no JUCE patch, but one buggy plugin view or DSP crash takes down the Song being recorded.
- **Manual latency nudge instead of calibration**: simpler, but users can't measure 18 ms by ear, and the spike already showed the measurement is cheap and stable.
- **Always calibrate, ignore reported latency**: robust, but blocks first use of every device behind a cable-patching step.

## Consequences

- `external/JUCE` carries a local patch, re-applied whenever JUCE is bumped. The spike's version is `spikes/au-monitoring/juce-force-auv2-oop.patch` on branch `spike/au-monitoring`.
- Plugin editors arrive as remote views. They open at a placeholder size and resize once the view attaches, so `DocumentWindow` must stay resizable to content. Set the native title bar *before* attaching an editor, because changing it afterwards re-parents the plugin's `NSView`.
- Watch `kAudioComponentInstanceInvalidationNotification` to detect a crashed hosting process. One `AUHostingService` process can host several units.
- The calibration offset is a per-machine device setting, not part of a Song.
- JUCE's `RuntimePermissions` is a no-op on macOS. Request microphone access through `AVCaptureDevice` before opening the audio device, or the TCC prompt blocks the message thread inside CoreAudio's device open.

## Amendment: recording details settled by the implementation (issue #26)

- **Placement under render-ahead.** The engine renders L (plan PDC) samples ahead (ADR 0003 amendment), so the first captured input sample was captured while the Track nodes rendered Song sample start + L. A Take's `origin` is `start + L − (input latency + output latency + L + calibration offset)`, which is `start − (input + output + calibration)`. `TakeCompensation.reportedLatencySamples` stores `input + output + L`.
- **The Take keeps every dry sample**; its Clip starts at the Pass start (the record point) or at `origin` if that is later, with `sourceOffset` set so each sample stays at its placed position. Input captured before the record point is in the file but not heard.
- **A Pass covers one continuous run of the transport.** It starts on the first playing block after record is pressed, and ends at stop, or when the transport stops or seeks.
- **Calibration store.** `~/Library/Application Support/Overdub/latency-calibration.json` keeps one offset per (input device, output device, sample rate); a missing entry is 0. `engine.device_opened` logs the offset in use.
- **Selftest.** On the built-in MacBook devices at 44.1 kHz with a 512 buffer, `--selftest loopback` measured `offset_samples` −821 and a jitter of 3 samples, matching the spike: the calibration flow (slice 18) stores `offset_samples` added to the current offset.
- **Overruns.** A block that does not fit an Armed Track's FIFO is recorded as silence of the same length, so later samples keep their place; the count is in `capture.pass_stopped` (`overrun_frames`).
- **Anchors** of a Pass (one per callback, ADR 0003) are returned in memory with the finished Pass (`capture::RecordedPass::anchors`), not stored in the package; slice 14 keeps what the Video Take needs.
- **Plain Monitoring** adds an Armed Track's input at its Track node, so it is delayed by the plan's PDC like the Track's playback. With no AUs (slice 12) that delay is 0.

## Amendment: Insert Chains settled by the implementation (issue #33)

- **Proof of the out-of-process path.** `patches/juce-force-auv2-oop.patch` also counts every AU JUCE creates through `AudioComponentInstantiate(..., kAudioComponentInstantiation_LoadOutOfProcess, ...)`: `juce::getAudioUnitOutOfProcessInstantiationCount()`. The `[au]` tests assert it rises by one per AUPeakLimiter load, and `plugin.instantiated` logs `out_of_process` (the count rose since the request) and `out_of_process_instantiations`.
- **Asynchronous, never blocking.** `plugin::AudioUnitLoader::instantiate` goes through `AudioPluginFormatManager::createPluginInstanceAsync` with a `PluginDescription` built from the slot's component codes (no scan, no synchronous `findAllTypesForFile`). The AU completion may arrive on any thread; the result is handed to the message thread with `MessageManager::callAsync`. Discovery (`findEffects`) lists `aufx`/`aumf` components, AUv2 and AUv3, without instantiating any.
- **One plugin per slot, across plans.** `plugin::InsertHost` owns each slot's processor and prepares it at the Song's rate and the device's block size. Every render plan runs it through an `engine::SharedInsertNode`, so a Song edit rebuilds the graph without re-creating a plugin. The node forwards blocks only after the plan's warm-up (the plan the audio thread plays may be running the same plugin), and never prepares or resets it. A plugin that loads, or whose reported latency changes, makes `OpenSong::poll` rebuild the plan (PDC); during a Pass that waits until the Pass ends, so the Pass keeps the latency it was placed with.
- **Master chain.** Every Track strip sums into the Master's Insert Chain, then the Master strip. Graph PDC covers both, so Take placement (`input + output + L`) includes every plugin's latency.
- **Tails.** The engine keeps rendering while stopped, so a plugin's tail rings out after stop. A plan's `tailSamples()` (longest Track chain tail + Master chain tail) is there for export.
- **Monitoring** goes through the Armed Track's chain (the live input enters at the Track node); Takes stay dry.
- **Known realtime exception.** The first out-of-process render on a thread makes AudioToolbox create its thread-local render context (`audioipc::current_render_context`, a 16-byte dyld TLV `calloc`), once per thread. The `[au][rt]` guard therefore starts at the audio thread's second block with AUs; every later block, plan swaps included, neither allocates nor locks.

## Amendment: Insert Chain UI and editor windows, settled by the implementation (issue #34)

- **Bypass** leaves the slot out of the render plan (`plugin::InsertHost::insertFactory`), latency included, so a bypassed Insert nulls against no Insert and PDC shrinks with it. Its plugin stays loaded with its state, so turning it back on is a plan rebuild, not a reload.
- **Editor windows** (`ui/PluginWindows.h`): one `DocumentWindow` per slot, created off the desktop, `setUsingNativeTitleBar (true)` first, then the content (badge strip + the AU's editor, or JUCE's generic editor when it has none), then `addToDesktop`; the title bar is never changed after. The window is resizable and resizes to its content; the content follows the editor's size, so a remote view that attaches at a placeholder size and then grows takes the window with it. `ui.plugin_window_opened` (`editor`, `width`, `height`, `native_title_bar`) and `ui.plugin_editor_resized` (`width`, `height`, `native_title_bar`) are the log a human pastes for the HITL check.
- **Lifetime.** A window holds its processor through a `shared_ptr`, so an edit or undo that releases the slot never leaves an editor without its plugin; the next refresh closes the window. Opening another Song closes every window.
- **Badge.** `plugin::hostingBadge` reads the AU's component flags: "AUv3 · out-of-process" or "AUv2 · out-of-process" (every AU goes through the out-of-process loader); test processors read "in-process".

## Amendment: the calibration flow as built (issue #39, answering issue #18)

- **When.** On demand, from Settings (below the device picker). A device opened without a stored offset for its input device, output device and sample rate shows the `ui.latency_not_calibrated` Notice at launch and after a device change, so first use of every device asks for it without blocking anything: until the user calibrates, reported latency is used (offset 0). Calibration is never automatic.
- **Guidance.** The panel names the device and rate, shows the offset in use ("Calibrated: −821 samples (−18.6 ms)" or "Not calibrated"), and tells the user to patch a cable from output 1 to input 1 (or turn the speakers up near the microphone) and turn off the interface's direct monitoring.
- **Measuring** is `capture::LoopbackRun` (`capture/LoopbackRun.h`), the same run `overdub --selftest loopback` makes: the bursts as a Backing Track, one Armed Track on input channel 0, a Pass through the real record path, `measureLoopback` on the placed Take. Its capture FIFO holds the whole run, so it cannot overrun. The window polls it; a run whose device stops calling back fails 5 s after it should have ended (`capture.calibration_timeout`). The open Song is detached from the engine while it runs and bound again afterwards; actions that would touch the engine show `ui.calibration_running`. Events: `capture.calibration_run_started`, `capture.calibration_run_finished` (the selftest's report fields).
- **Storing.** A usable result (bursts found, jitter ≤ 5 samples) offers "Use This Calibration", which stores the offset in use plus the measured `offset_samples` (a zero result offers nothing). The live engine and the open Song place the next Pass with it at once; the device is not reopened. Takes already recorded keep their placement.
- **Shown** only in Settings; `engine.device_opened` and each Take's `compensation` keep logging the offset applied.

## Amendment: plugin crash recovery as built (issue #40, answering issue #19)

- **Detection.** `plugin::InvalidationWatch` observes `kAudioComponentInstanceInvalidationNotification` on the local notification center (any object). Core Audio posts it from its own thread, possibly more than once per crash, with the AU instance in `userInfo["audioUnit"]`; the watch hands that instance to the message thread, and `InsertHost::audioUnitInvalidated` matches it against each ready slot's `AudioUnit` (`plugin::audioUnitHandle`), skipping any slot whose load was requested after the notification was received: the watch numbers each notification on receipt (`InvalidationWatch::Receipt`), and a slot remembers the last number when its load was requested, so a newly loaded AU that reuses a dead AU's address is never marked crashed, while a crash during the load is still caught (issue #66; the skip logs `plugin.invalidation_unmatched` with `reused_address`). A repeated notification for a process already reported dead (same `userInfo["Service PID"]`) is handed on with the Receipt of that process's first notification, so a repeat that arrives after a reload was requested is skipped too, while the reloaded AU's own crash (a new hosting process) still crashes its slot (issue #79). This assumes a pid is not reused by another hosting process while the app runs. Every unit a dead `AUHostingService` hosted gets its own notification, so each of its slots crashes on its own; an unmatched or repeated notification is ignored (`plugin.invalidation_unmatched`, debug).
- **The slot is bypassed at once, never reloaded mid-Pass.** The host sets the slot's crash flag first: every `engine::SharedInsertNode` running it (the plan playing, a retired one, an export's) stops calling the dead plugin at its next block and passes its input through delayed by the latency it reported, so the plan's PDC still lines the chain up. The slot becomes `crashed`, its processor is released (plans keep it alive until freed off the audio thread), its editor window closes, its chip reads "(crashed)", and `plugin.invalidated` (warn: slot_id, name, component, version, latency_samples, tail_seconds, out_of_process, crashes, will_reload) is logged. The next plan leaves the slot out as a bypass would; during a Pass that waits until the Pass ends, as every plan change does.
- **Recording continues.** A Pass is never stopped by a crash: Takes are dry, so they lose nothing; only Monitoring and playback lose that effect. The user sees the `ui.plugin_crashed` Notice (one per poll, naming every slot that crashed), never a modal.
- **Reload from the last saved state.** Once no Pass or export runs, `OpenSong::poll` reloads each crashed slot through the normal asynchronous loader with the state its Song slot holds then: the state captured at the last history step or debounced write. Changes made in the plugin after that capture are lost: a dead process's state cannot be read.
- **Repeated crashes.** A slot reloads after its first `plugin::maxCrashReloads` (2) crashes. Its third crash reports `ui.plugin_crashed_repeatedly` (Notice) instead, and the slot stays crashed and left out while the Song is open; it keeps its Song entry and saved state, so reopening the Song (or removing it and undoing) tries it again. Clicking it shows the same Notice.
- **Exports.** A crash discards an export only when the export's plan renders the crashed slot (`ui.export_plugin_crashed`, an Alert: its file would miss the effect). The slots it renders are those not bypassed and loaded when its render was built (`InsertHost::renderedSlots`, the rule `insertFactory` builds plans by). While it still waits for the audio ("Preparing…") its render is not built yet: it will be built from the Song as it is then, and a crashed slot would be left out of it, its effect missing from the file. So while it waits, a crash of any slot the Song plays (not bypassed) discards it, including a slot that finished loading during the wait (issue #78; before, only the slots the Song's plan rendered at request time counted, and such a slot rendered dry). A crashed slot is not reloaded during an export, so when the render is built, a slot the Song plays that is crashed and would still reload (it crashed while bypassed and was played again during the wait) also discards it with `ui.export_plugin_crashed` instead of rendering dry. A slot that crashed for good is left out of the render, as playback leaves it out. A crash in any other plugin (bypassed, or added or still loading after the render was built) leaves the export running and its file intact. An export that already finished but was not yet collected has its file deleted by the same rule.
- **Inserts removed during an export (issue #65).** An export renders the Song as it was when its render was built: an Insert an edit removes meanwhile keeps sounding in that export until it ends. Its slot stays hosted until then (`InsertHost::sync` with `RemovedSlots::keep`; slots added meanwhile still load), so a crash of its plugin is still heard and discards the export; once the export ends the slot is released and never reloaded.
- **Tests** never kill `AUHostingService` (it may host other apps' units): they post the notification themselves for a loaded AUPeakLimiter (`[au][crash]`) or call `InsertHost::pluginCrashed` with a test processor.
